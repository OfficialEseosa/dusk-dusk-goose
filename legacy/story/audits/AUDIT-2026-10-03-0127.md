## 5.1 Summary

**Phase and what was tested.** Skeleton/MVP. I read every source file, ran the type check (clean) and the 9 unit/transport tests (all pass), and drove the running local game with two fully isolated Chromium contexts: desktop 1280×800, emulated phone landscape 844×390 with touch, emulated phone portrait 390×844, emulated hidden tabs, and a simulated Wi‑Fi‑to‑cellular switch (a local proxy that cuts the browser side while the server hears nothing). No console errors or warnings appeared in any run.

Not tested: real phones, real Safari, real audio output, a public network, the existing Playwright suite (not re-run because its files were being edited mid-audit; the README claims it passed).

**Verdict: not demo-ready for a judge on two phones.** The single biggest reason is that **there is no public URL, and it is unresolved whether the place ChatGPT publishes to can run this game at all**: the design needs one long-lived Node server holding rooms in memory with an open realtime connection per player. If the publishing target is static-only, the multiplayer architecture cannot ship as built. Settle that before anything else.

Behind that, in order: on a phone held sideways the scene does not fit and the game starts scrolled past it; tapping objects in the scene does nothing; any hidden tab freezes both players; and the visuals are an openly labelled graybox.

What is good, briefly: the server is properly authoritative, role races and duplicate actions are handled, radio text is escaped and rate limited, reconnect tokens are unguessable, private clues are sent only to the right player, and the full three-act story is completable. The foundation is sound. The problems are at the edges a judge touches first.

**Changes since last audit:** none to compare.

## 5.2 Architecture map

- **Stack.** TypeScript throughout. Client: Vite, no framework, one stylesheet. Server: plain Node HTTP plus Socket.IO. No database, no accounts, no external services, no image or audio files.
- **Files.** `shared/protocol.ts` holds the message and state types. `server/game.ts` is the rule book (one `GameRoom` class: phases, puzzles, hints, what each player is allowed to see). `server/story.ts` holds the narration line for each phase. `server/index.ts` owns rooms, sockets, rate limits, cleanup, and serves the built client. `src/main.ts` is the whole client (networking, rendering, input, sound). `src/scene.ts` draws the pictures as inline vector shapes. `src/content.ts` holds chapter titles and quick radio replies.
- **Sync flow.** A player taps something. The client sends an `action` message. The server checks it against the current phase and the partner's flashlight position, changes the room, then sends each player their own full `snapshot` (their private text and labels differ). The client throws away the whole screen and redraws it from that snapshot. Flashlight position travels separately as a lightweight `beam` message about 16 times a second and is relayed to the partner. There are no partial updates: every durable change is a full snapshot with a revision number.
- **Timed moments.** The server stamps when each phase began. The opening blackout is drawn by each client comparing its own clock (corrected by the server time in the last snapshot) with that stamp. The final goodbye is timed entirely on the server (100 ms tick, one second of overlap).
- **Rooms.** Five-character codes from an unambiguous alphabet, held in server memory. Max two players. A room is deleted after 30 minutes with nobody connected, or 12 hours after creation. A server restart loses every room.
- **Rejoin.** On joining, the server issues a secret token. The client keeps it in per-tab session storage and presents it automatically on reconnect or refresh.
- **Pause.** If either player is disconnected or their tab is hidden, the room is paused: timers stop and every action is refused.

## 5.4 Rubric estimate

- **Execution: 2 / 5.** A required item (public URL) is missing and the hosting question is open. The rules engine is reliable on two desktop windows, but the phone-landscape experience and two-tabs-in-one-window testing are both broken.
- **Creativity: 3 / 5.** The premise (asymmetric views, a secret, a shared flashlight) is strong and would score 4. The implementation currently plays as pressing labelled buttons in a list, which hides the idea.
- **Usefulness / Value: 2 / 5.** The emotional arc is complete and the writing is decent, but the play itself is not yet delightful: no darkness, no discovery, no sound, and several puzzles can be clicked through.
- **Polish and Thoughtfulness: 2 / 5.** The page footer literally reads "A PLAYABLE GRAYBOX / ORIGINAL TEMPORARY ART". Text on a phone is 7–11 px. Edge cases on the server are handled thoughtfully; edge cases on the screen are not.

## 5.5 Findings

Sorted by severity, then by how cheap the fix is.

### Blocker

**A-01 — No public deployment; hosting compatibility unknown. Confirmed (absence), hosting itself not verified.**
- Where: `README.md` ("Limits and next milestone"), `package.json` scripts, `server/index.ts` line 14 and lines 329–340.
- What happens: the game runs only on your machine. Nothing in the repo records a public address.
- Why: the build needs a continuously running Node process that accepts realtime connections and keeps rooms in memory. That means one instance only (two instances would split players across different room lists), no sleeping, and WebSocket support. I do not know whether ChatGPT's publishing target provides this. Two further traps: the start command depends on a development-only package, so a host that installs production packages only will fail to start; and the development inspection endpoints stay open unless the environment is explicitly marked production (E-01).
- Why it matters: a challenge requirement is unmet. Execution.
- Correct: a public address where two phones on different networks can create and join a room, with the realtime connection confirmed working and the inspection endpoints closed.

**B-01 — A hidden tab freezes the game for both players. Confirmed (emulated tab visibility).**
- Where: `server/game.ts` `paused` getter (lines 65–70), `maybeStart` (132–139), the refusal in `action` (line 296), `visibility` (125–131). Client: the `visibilitychange` listener in `src/main.ts`.
- What happens: open the game in two tabs of one browser window, create and join, pick houses, press Ready in each. The night does not start, because whichever tab you are not looking at counts as "away". Mid-game, every tap in the visible tab is refused with "Waiting for both players to return." During the audit ChatGPT added a lobby message explaining this ("Keep both game windows visible side by side"), but the rule itself is unchanged.
- Why: the server treats "tab not visible" the same as "player disconnected" and blocks everything, not just timed moments. On Windows, Chrome also reports a fully covered window as hidden, so two maximized windows behave the same way.
- Why it matters: a judge testing alone on one laptop, which is the most likely way this gets evaluated, cannot play. On phones, a player glancing at a text message freezes their partner. Execution, Polish.
- Correct: a hidden tab never blocks the lobby from starting and never blocks the other player's actions. At most, the two genuinely timed moments (the opening blackout and the final one-second signal) wait for both players. This is a case where **the spec is wrong** (Section 7, "pause when either player's tab is hidden") and should be narrowed.

### High

**C-01 — On a phone held sideways the scene does not fit, the game opens scrolled past it, and a finger on the scene cannot scroll. Confirmed (emulated 844×390 touch device).**
- Where: `src/style.css` `.game-screen` (lines 320–327), the 1000 px breakpoint (line 704), `.scene` `touch-action` (line 349), header height (line 99). Client `render` in `src/main.ts`.
- What happens: (1) After tapping Ready, which sits low on the lobby page, the game appears with the page still scrolled down: only 36% of the scene was on screen during the date card and blackout. (2) Scrolled to the top, the header plus chapter line take 126 px of a 390 px screen, so the scene's bottom edge is cut off and the objective, the instructions, and every Interact button are below the fold. (3) Swiping with a finger on the scene does not scroll the page at all; swiping on the narrow radio column does. The scene is about two thirds of the screen width, so most swipes do nothing.
- Why: the layout was designed for desktop and tall portrait. Scroll position is never reset when the screen changes from lobby to game. The scene blocks all touch gestures so the flashlight can follow a finger, which also blocks scrolling.
- Why it matters: the brief says the game is played in landscape, and this is the worst orientation. The synchronized blackout, the signature opening moment, happens mostly off-screen. Execution, Polish.
- Correct: on a sideways phone the whole scene, the current objective, and whatever the player must tap are visible together without scrolling, and the game always begins with the scene in view.

**F-01 — Tapping objects in the scene does nothing; the real controls are a button list underneath. Confirmed.**
- Where: `src/main.ts` `game` (the `.hotspot` buttons carry only an aim attribute), `bind` (aim handlers versus interact handlers), `aim` (returns early without a flashlight). `src/content.ts` `actorCanInteract`.
- What happens: first task is "Find both flashlights". The flashlight is drawn on the bed with a "+" marker. Tap it: nothing happens, no message. The only way forward is a small "Interact" button in a list below the scene (off-screen on a sideways phone, per C-01). The helper text reads "Aim and interact are separate. Your friend may need to light the object first."
- Why: scene markers were wired to aiming only, and aiming is disabled until you own a flashlight.
- Why it matters: this is the first ten seconds of play. The brief's 30-second rule fails here. It also turns every puzzle into list-clicking rather than touching the world. Usefulness, Polish, Creativity.
- Correct: tapping an object in the scene acts on it when the player is allowed to, and gives a short in-world reason when they are not. The list remains as a keyboard and accessibility alternative, not the main path.

**F-02 — There is no darkness, the flashlight reveals nothing, and the art is a flat graybox. Confirmed (screenshots).**
- Where: `src/scene.ts` (all drawing, the lighting group, the two glow gradients), `src/content.ts` `ASSETS` (every slot empty), `src/style.css` lines 2 and 141 (two named fonts that are never loaded, so every device falls back to defaults), footer text in `render`.
- What happens: after the "blackout" the scene is as bright as before. Your own flashlight is a faint pale patch; your friend's is an amber patch. Nothing is hidden and nothing is revealed by light, except one text label in the shelf puzzle. There are no depth layers, no movement, no sound bed. The footer announces it is a graybox.
- Why: the spec scheduled art for a later milestone and told ChatGPT not to make darkness hide anything.
- Why it matters: this is exactly the gap you noticed. "Lighting is the star" was the brief's art direction and it is the game's one distinctive mechanic. Creativity, Usefulness, Polish.
- Correct: after the power cut the scene is genuinely dark and the beam is what lets you see. See the note on 3D in 5.6 before asking for this.

**B-02 — If your partner leaves for good, you are trapped on the pause screen. Confirmed.**
- Where: `server/index.ts` `leave` handler (lines 153–172, refuses outside the lobby). `src/main.ts` `render` (the "Start fresh" button is only offered when no game is on screen) and the logo link.
- What happens: mid-game, close one player's browser. The other sees "We'll wait for each other" indefinitely. There is no leave, quit, or new-game control. Clicking the logo reloads the page and drops you straight back into the same paused room.
- Why: leaving is only permitted in the lobby, and the stored seat is reused automatically on every load.
- Why it matters: a judge who closes one window cannot start over without knowing to open a brand-new tab. Polish, Execution.
- Correct: the pause screen offers a clear way out after a short wait, which returns to the title and forgets the seat.

**B-03 — Reopening the invite link in a new tab locks the player out of their own game. Confirmed.**
- Where: `src/main.ts` `saved` and `enter` (seat kept in per-tab session storage; a second value written to local storage under "maple-last-room" is never read). `server/game.ts` `addPlayer` (line 86).
- What happens: mid-game, the phone discards the tab, or the player taps the invite link again from their messages. A new tab opens with the room code filled in. Joining says "This night already has two players." Their partner is stuck paused (B-02).
- Why: the secret token lives only in the original tab. A new tab has no token, and the server correctly refuses to trust a name.
- Why it matters: this is the brief's rejoin requirement (3.8) in its most common phone form. The brief's "same code and name" approach would be insecure; the token is the right idea, stored in the wrong place. Execution.
- Correct: the same browser reopening the same room, by link or by code, gets its seat back. Two tabs on one computer can still be two different players (which is why the fix needs care).

**H-01 — The whole screen is rebuilt on every update, which eats taps and disturbs typing. Confirmed for taps and form fields; suspected for phone keyboards.**
- Where: `src/main.ts` `render` (replaces all page content) and `bind` (reattaches every handler), called from the `snapshot` handler.
- What happens: (1) Press down on a button; if any update arrives before you lift (your friend sends a radio message, asks for a hint, toggles their signal), the button under your finger is replaced and the tap is silently lost. Reproduced. (2) On the title screen, type a name and a wrong room code: after the error both fields are wiped. Reproduced. (3) Suspected: on a phone, typing a radio message while an update arrives destroys and recreates the text box. The code tries to restore focus, but phone browsers generally will not reopen the keyboard without a touch, and predictive-text composition is lost. (4) The blackout fade can restart if an update lands during the opening.
- Why: there is no partial updating; everything is torn down and redrawn.
- Why it matters: lost taps feel like a broken game, and they happen more when both players are active, which is the whole point. Execution, Polish.
- Correct: an incoming update never cancels a tap in progress, never clears what the player has typed, and never closes the keyboard.

### Medium

**B-04 — After a network switch the player sees a wrong, alarming error and is silently out of the room for about ten seconds. Toast confirmed; permanent-stuck variant suspected.**
- Where: `server/game.ts` `reconnect` (lines 104–118), `server/index.ts` heartbeat settings (lines 104–109), `src/main.ts` `emit` (the automatic retry only runs when no game is on screen).
- What happens: I cut one player's connection the way a Wi‑Fi‑to‑cellular switch does (browser side drops, server hears nothing). Within two seconds the player's own screen showed "This seat is already open in another tab. Close that tab first." with the header still saying "Radio connected". That lasted roughly ten seconds, then cleared and play continued. During that window the player is not in the room. I did not isolate why it recovered; the code's own retry is skipped in this situation, so I would not rely on it.
- Why: the server takes up to 15 seconds to notice the old connection is dead and refuses the token while it thinks the seat is occupied.
- Why it matters: real phones do this constantly. The message blames the player for something they did not do. Execution, Polish.
- Correct: a returning player with the right token takes over their own seat immediately, the old connection is dropped, and no error is shown.

**B-05 — A failed rejoin leaves a dead game on screen. Confirmed by code trace, not reproduced.**
- Where: `src/main.ts` `emit` and `render`.
- What happens: if the room no longer exists when the client reconnects (server restarted, room expired), the old game stays on screen with an error and no "Start fresh" button, because that button only appears on the title screen. A manual refresh fixes it.
- Correct: when the room is gone, the player is returned to the title with a clear explanation.

**B-06 — Several "cooperative" steps can be finished without cooperating. Confirmed.**
- Where: `server/game.ts` route case (lines 464–476; not in the needs-light list at 428–434), passage case (448–460), `illuminated` (200–203).
- What happens: in the route puzzle the player at the fence finished alone in five clicks by trying each landmark; wrong guesses cost nothing and no light is required. In the passage, wrong steps also cost nothing. A beam left pointing at the key from the previous step already counts as lighting stepping point 3.
- Why it matters: the pitch is "you need each other". A judge who clicks around will get through without talking. Creativity, Usefulness.
- Correct: each step needs a fresh, deliberate act from the partner, and guessing is gently discouraged (for example, a short pause after a miss).

**C-02 — No rotate prompt, fullscreen control, or Home Screen tip. Confirmed.** The brief requires all three (3.2); the spec removed them. Portrait actually works better than landscape today. Decide: either fix landscape (C-01) and add the brief's setup items, or commit to portrait and update the brief. Do not leave it between the two.

**C-03 — Sound is one beep. Confirmed by reading; iPhone behavior not verified.**
- Where: `src/main.ts` `beep`, `unlockAudio`.
- What happens: a tone plays on phase change. No ambience, no radio crackle on messages, nothing stops at the blackout. Sound is only unlocked by the Ready button or the sound toggle, so after a mid-game refresh there is no sound for the rest of the night, and nothing resumes it after a phone interruption.

**F-03 — Hints do not escalate and the automatic hint is nearly invisible. Confirmed.**
- Where: `server/game.ts` `hint` (lines 555–594), `server/index.ts` hint handler; `src/main.ts` `animation` (the 50-second nudge).
- What happens: after 50 seconds without progress, the radio header gets a thin border. No hint text appears by itself. The manual button has two real levels, not three. One hint reads "Keep both tabs visible; the blackout arrives after four seconds", which is developer language.

**F-04 — Text is too small on phones. Confirmed (measured).** Role label 7 px, scene caption 9 px, radio messages 11 px, quick replies 35 px tall. The brief requires readable text on a small phone.

**E-01 — Development endpoints are open unless the host is explicitly set to production. Confirmed.** `server/index.ts` lines 14 and 28–69. Anyone who knows a room code could reset that room. Ties to A-01.

**B-07 — Blackout alignment degrades on slow links. Confirmed by code trace.** The client's clock correction is recomputed from each snapshot's arrival time with no allowance for delay, and the move from the date card to the dark room arrives as an ordinary message. On one machine it is aligned; on a slow cellular link each phone will be late by its own delay. Likely acceptable, but it is not the "documented tolerance" the spec asks for.

### Low

- **H-02 Dead or unused pieces.** The "maple-last-room" stored value is never read. Every `ASSETS` slot is empty. The server counts mistakes but nothing uses the count (the spec's "make the route clearer after repeated trouble" is not built).
- **H-03 Fragile file.** `src/main.ts` builds each whole screen as a single very long line (`title`, `lobby`, `game`). Any ChatGPT edit there risks breaking neighbours. Worth splitting when H-01 is fixed, not before.
- **D-01 Serving.** The built script is 74 KB (25 KB compressed) and there are no images or audio, so load size is not a problem today. The server sends no compression or caching headers and answers anything other than GET with an error, which some hosts' health checks use.
- **E-02 Cross-origin setting accepts any site.** Harmless now; tighten at deployment.
- **F-05 Ending votes.** If one player picks replay and the other picks lobby, both just see "Waiting for your friend's matching vote" with no indication of what the friend chose.
- **G-01 Later phases.** Voice radio could be added as a new message kind, but the 8 KB message size cap would reject any audio clip, so clips need a different path. Story text is data (`server/story.ts`); puzzle rules are hand-written per phase inside one large function, which is fine for three acts and not worth abstracting.

Security checks that passed: radio text is escaped on display (the existing tests inject markup and confirm it shows as text), length is capped at 180 on the server, radio is limited to 8 messages per 10 seconds, every socket is limited to 35 messages a second, room codes have about 33 million combinations, a stranger cannot join a full room or take a seat by name, clients cannot set the phase, and there are no keys or secrets in client code.
